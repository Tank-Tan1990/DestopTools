- 产物：`DestopTools/release/DestopTools.exe` = **1,277,440 B @ 2026-09-22 01:40:54**（上轮 1,272,320 B → +5120 B），`NMAKE_EXIT=0`

## 一、这轮抓到的真凶：缓存上限 6 页 < 你的 7 个分类

上一轮修的"几何抖动"与"搜索框回环"都是真问题，但不是你这次看到的现象的主因。**主因是缓存条数上限**：

```cpp
// 修复前
void IconGridWindow::trimPageCache() {
    const int kMaxCachedPages = 6;      // ← 写死 6
    while (m_pageOrder.size() > kMaxCachedPages) { /* 丢弃最久未用的页 */ }
}
```

而你的实际分类（从 `%APPDATA%\DestopTools\DestopTools.ini` 读出）：

```
IconGridWindow/categoryOrder = 快捷方式, 目录, 文档, 压缩, 图片, 其它, 网址      ← 共 7 个
```

7 > 6 ⇒ **来回切换时，每切到第 7 个就会把队首那页（往往正是"下一次要切回的那页"）淘汰掉**，
切回去只能重建 —— 现象就是"**多切换几次**又会看到加载"。这与你的描述完全吻合：不是每次都刷新，
而是切够多次必然撞上一次。

另外，分类变多时这个上限还会让"改一次分类"连累全部缓存：原先 `rebuildGrid()` 开头是
`invalidateCategoryPages()`（**所有**分类的页一起作废），所以你**新增/删除一个分类之后，每个分类
切回去都要重刷一遍** —— 这正是你这次补充的两点要求。

## 二、修法（4 项）

### 1. 缓存上限改为按分类总数给足（不再写死）

```cpp
const int kMaxCachedPages = qBound(8, m_allItems.size(), 24);
```

一页就是一个分类的全部按钮，全缓存的总量 = 全部桌面条目，与"桌面本身那么多图标"同阶，可接受。
下限 8 兜住分类很少的情况；上限 24 兜住"分类极多"的极端（那时优先保内存，允许 LRU 淘汰）。

### 2. 命中判据从"全局数据代次"改成"**逐页内容签名**"（关键）

- 每个缓存页记录 `signature` = 页内按钮的 `sourcePath` 序列（**顺序敏感**，拖拽排序后必须重建）。
- 装回时与"该分类当前条目的签名"逐项比对：**相同 → 复用；不同 → 丢弃重建**。
- 于是**新增/删除分类、往别的分类里增删文件，都只影响自己那一页**，不再连累全部缓存。
- 删掉了 `m_pageGeneration` 与 `rebuildGrid()` 里的全局 `invalidateCategoryPages()`：
  后者现在只在**视图档位切换**（大/中/小/列表，全部页的图标像素都过期）时显式调用。

### 3. 新增 `pruneCategoryPages()`：只收走"孤儿页"

```cpp
// 分类被删除 / 改名后，其缓存页的 key 已不在 m_allItems 里 → 销毁，避免白占内存。
// 其它分类的页一概不动（这是"增删分类不连累别人"的另一半）。
```
在 `rebuildGrid()` 里调用一次（分类集合变化必然走重建）。

### 4. 收纳盒（含新建/删除）天然共用同一套

收纳盒窗口与主整理窗口是**同一个类** `IconGridWindow`，页缓存是**每窗口实例**的成员：

- **新建收纳盒** → 自己的缓存从空开始，"第一次切换构建、之后复用"照常生效。
- **删除收纳盒** → 窗口销毁时 `m_pageCacheHost`（窗口子控件）连同其下所有缓存按钮一并析构，无泄漏。
- **收纳盒内增删分类** → 与主窗口同一条路径（`setItems` → 内容签名 → prune 孤儿页）。

### 附带（上一轮已修，这里一并保留）

- `relayoutGridForGeometry()`：几何变化（窗口缩放/滚动条出现消失）只重排、不重建、不动缓存。
- `setSearchText()` 早退：断掉"切换分类 → 助手面板 clearSearch → 又回到 setSearchText"的回环。
- `setItems()` 内容相同则整体早退：MainWindow 有近 20 处 `setItems()` 调用，内容没变时不再
  白重建网格、白重建整条标签栏（后者会让高亮跳一下，很像"又刷新了"）。
- 装回页时**还原滚动位置**（`CachedPage::scrollY`），避免"回到顶部"被当成重新加载。

### 顺带加了诊断日志（默认关闭，不影响性能）

若还复现，打开后一次即可定位到具体是哪条路径在重建：

- 打开方式（任选其一）：环境变量 `DESTOPTOOLS_DIAG=1`，或 INI 里写 `[Diagnostics] traceEnabled=true`
- 日志文件：`DestopTools\release\DestopTools_trace.log`
- 关键行（都带 `[grid]` 前缀）：
  - `switchPage A -> B parkOld=1 cached=N`：换页动作与缓存规模
  - `adoptPage HIT/MISS cat=... n=...`：**命中还是重建**（MISS 就是"刷新"）
  - `rebuildGrid cat=... cachedPages=... cats=...`：谁触发了重建
  - `prunePage / trimPage / invalidatePages`：缓存被收走的原因

## 三、修复后的行为（对照你的三点要求）

| 场景 | 修复前 | 修复后 |
|------|--------|--------|
| 来回切 7 个分类 | 每 7 次至少淘汰 1 页 → 周期性重建 | 全部 7 页都在缓存里 → **零重建** |
| 新增一个分类 | 全部缓存作废，之后每个分类切回都重刷 | 只新分类首次构建，**其它分类照旧复用** |
| 删除一个分类 | 同上全废 | 只销毁被删分类的页（prune），**其它分类不受影响** |
| 新建收纳盒 | 同上（且是主窗口全废） | 收纳盒独立缓存，互不影响 |
| 在某个分类里增删/排序文件 | 全部作废 | 只该分类签名变化 → 只它重建，其它复用 |
| 切回来 | 回顶部 | 还原上次滚动位置 |

## 五、请实测的点

1. **来回切 7 个分类十几次** —— 每个分类切回都应立即出现，不再有加载过程。
2. **新增一个分类** → 切过去（首次构建，正常）→ 再切回其它老分类：应**直接出现**。
3. **删除一个分类** → 其余分类切回应**直接出现**。
4. **新建一个收纳盒** → 在它里面切几个分类、再切回：同样应直接出现。

里含 `[grid]` 的行发我 —— 里面会直接写明是 `adoptPage MISS`、`trimPage evict` 还是某次 `rebuildGrid`。
