## 0. 一句话结论

**语义实现本来就是对的（20/20 实测通过），缺的是"生效时机"** ——
消费者只在**构造窗口**和**窗口显示**时读一次设置，而用户在设置中心改的时候窗口**正开着**，
`showEvent` 不会再发一次，于是永远停在旧值。用户看到的「设置了但没反应」就是这个。

已补齐**设置变更广播 + 就地热更新**链路，改完立刻按新语义工作（不必关窗口、不必重启）。

## 1. 缺口定位（为什么"没反应"）

| 环节 | 状态 |
|---|---|
| 设置中心写盘 `Appearance/tagSwitchMode` | ✅ 正常（上一轮已修好两对单选钮互踩） |
| `IconGridWindow` 消费该键 | ✅ 存在（`loadTagSwitchMode()` / `activateCategoryTab()` / `HoverEnter`） |
| **消费时机** | ❌ **只有构造函数 + `showEvent()`** —— 窗口正开着时改设置，永远不会重新读 |

补充事实：`SettingCenterDialog` 里那个通用的 `signals: void settingChanged(key, value)`
**从来没被任何代码 emit 过**（moc 元数据里有、实现里没有）——所以此前没有任何"改完就通知"的通道。

> 📌 这是"空设置/孤岛设置"问题的**第二种形态**：不是没有消费者，而是消费者**错过了刷新时机**。
> 判据应扩成三查：①有没有消费者 ②读的是不是同一个 key ③**改的时候消费者会不会被通知**。

## 2. 修复（只动这一项，语义一字未改）

| 文件 | 改动 |
|---|---|
| `thememanager.h` | 新增 `static void notifySettingChanged(const QString& key, const QVariant& value)` ＋ 信号 `settingChanged(key, value)` |
| `thememanager.cpp` | 实现 `notifySettingChanged`（空 key 直接返回，`emit instance()->settingChanged(...)`） |
| `icongridwindow.h` | 新增 `void reloadTagSwitchMode()` 声明 |
| `icongridwindow.cpp` | 构造函数订阅 `settingChanged` 并按 key 过滤；实现 `reloadTagSwitchMode()`；`showEvent()` 改为复用同一函数；补 `#include <QVariant>` |
| `settingcenterdialog.cpp` | `saveSettings()` 写盘该键后立即广播 |

### 关键设计：广播与样式重刷**严格分离**

`notifySettingChanged` **不触发任何样式重刷**（不 repolish、不 `dispatchTargets`），
与 `themeChanged()` 是两条独立链路 —— 所以可以放心在每次 `saveSettings()` 里调用，不会有性能代价。
消费方按 key 过滤，收不到自己 key 的窗口直接返回。

`reloadTagSwitchMode()` 只在**模式真的变了**时才 `applyTagSwitchModeToTabs()`
（`setAttribute` 会触发重绘，无谓下发纯属浪费）。
