## 一、你的两条诉求

1. 收纳盒中分类对应的图标**已经缓存好了**，交换图标时应该**只是交换位置**，不必重新刷新加载。
2. **从 Dock 拖拽进收纳盒**的图标，同样不需要重新刷新加载。

两条指向的是同一个病灶：**收纳盒界面每次都在做"全量重建"，而不是"只动变化的那一处"**。

---

## 二、根因（改之前实际发生的事）

### 2.1 盒内交换两个图标的位置 → 全屏所有盒子被推倒重建

```
FenceBox::dropEvent
  → emit itemDropped(id, sourceCat, targetCat, targetIndex)
    → IconGridWindow::onFenceItemDropped
      → reorderItemInCategory(category, id, targetIndex)      ← 数据只换了个排列
        → rebuildGrid()
          → buildFences()                                     ← 🚨 把**全部** FenceBox 销毁重建
            → 每个 FenceBox::setItems() → FenceBox::rebuild()
              → 每个盒内按钮 deleteLater() + new DesktopIconButton()
                → 图标按当前像素重取一遍（走 g_iconCache，但 setIcon / 缩放 / 上传纹理一样不少）
```

**双重浪费**，而且不止"多刷一次"：

- 变动的只有 `category` 那**一个**盒子，却重建了**所有**盒子；
- 关键时序坑：`drop` 事件是在 `QDrag::exec()` **内部**同步派发的，那一刻 `m_iconDragInProgress` **仍是 `true`** → `rebuildGrid()` 开头的冻结闸门直接把请求记成 `m_pendingRebuild = true` 并返回 → 等 `exec()` 返回、`setIconDragInProgress(false)` 才**补做**真正的那次重建。

⇒ 用户观感正是你描述的："松手 → 顿一下 → 整个收纳界面**闪一下**全部重刷"。**为了换两个图标的位置，付出了全屏重建的代价。**

### 2.2 从 Dock 拖一个图标进收纳盒 → 同样全屏所有盒子被推倒重建

```
DesktopMirrorWindow::onIconDragEnd
  → MainWindow::scheduleDockItemsIntoBox()          （延迟一拍执行）
    → 改 m_allItems / targetBox->items
      → for (auto& box : m_boxes) box.window->setItems(box.items);   ← 🚨 对**每一个**盒窗口都推一次
        → IconGridWindow::setItems() 尾部**无条件** rebuildGrid()
          → buildFences()                                            ← 全部盒子再重建一遍
      → m_gridWindow->setItems(m_allItems)                           ← 主窗口也来一次
```

只往**一个**盒子里加**一个**图标，代价却是"所有盒子的所有图标全部重建"。而且 `setItems()` 有近 20 处调用点，这条重建链在各类刷新/同步路径上会被反复触发。

## 三、改了什么（4 个文件 / 9 处）

### A. 新增：顺序变化的廉价出口（"只交换位置"）

| # | 位置 | 内容 |
|---|---|---|
| A1 | `fencebox.h/.cpp` `FenceBox::reorderItemsInPlace()` | 按新顺序把**现有按钮**放回布局。**不 deleteLater、不 new、不重取图标** —— 按钮对象、图标位图、信号连接原地保留。集合对不上一律返回 `false` |
| A2 | `icongridwindow.cpp` `IconGridWindow::tryReorderInPlace(cat)` | 分发口：盒视图 → 定位 `cat` 那**一个** `FenceBox` 做原地重排（其余盒子一个控件都不动）；网格视图 → `reorderGridButtonsInPlace()` |
| A3 | `icongridwindow.cpp` `reorderItemInCategory()` | 末尾 `rebuildGrid()` → **`if (!tryReorderInPlace(category)) rebuildGrid();`**（不适用才退回原路径） |
| A4 | `icongridwindow.cpp` `flushPendingGridWork()` | 解冻后**优先原地重排**，不适用才全量重建。替换了 `onContextMenuVisibleChanged` / `onIconEditingChanged` / `setIconDragInProgress` 三处原先"无脑 `rebuildGrid()`"的补做逻辑 —— **2.1 里那个"顿一下再全屏重刷"就是在这里被消掉的** |

### B. 新增：按分类增量刷新（"Dock 拖入只加一个图标"）

| # | 位置 | 内容 |
|---|---|---|
| B1 | `fencebox.h/.cpp` `FenceBox::applyItemsDelta()` | **复用**集合内已存在的按钮，只为**新增项**新建按钮、把**移除项**的按钮销毁，再按新顺序重排。增删幅度 > 8 直接放弃 |
| B2 | `fencebox.h/.cpp` `FenceBox::createItemButton()` | 🚨把 `rebuild()` 里"建按钮 + 接 8 组信号"抽成**唯一一份**，`rebuild()` 与 `applyItemsDelta()` 共用 —— 两条路径各写一份接线，漏掉任何一个 `connect` 都会让那条路径下的 **F2 / Delete / 右键菜单 / 改名静默失效** |
| B3 | `icongridwindow.cpp` `applyItemsDeltaInPlace(next)` | 两阶段：① **只读预检**（分类集合一致、变化分类 ≤ 4、增删 ≤ 8、新旧路径交集 ≥ 一半）→ 任一条不满足就 `return false`；② 执行时**只更新变化分类对应的那一个盒子**，其它盒子完全不动 |
| B4 | `icongridwindow.cpp` `setItems()` | 在 `m_allItems = normalized` **之前**调用 `applyItemsDeltaInPlace()`（要拿旧值比对）；命中则末尾不再 `rebuildGrid()`，改为清一次 `m_dragSourceTab`（`buildTabs()` 刚重建过标签按钮，与 `rebuildGrid` 同款收口） |

### C. 新增：收纳盒「顺序保护」（防止交换结果被冲掉）

| # | 位置 | 内容 |
|---|---|---|
| C1 | `icongridwindow.cpp` `setItems()` | 盒窗口收到 `setItems` 时：某分类的条目**集合**与窗口内完全一致（只是顺序不同）⇒ **一律沿用窗口内顺序**。集合真的变了（增/删）则照收 |
| C2 | `icongridwindow.cpp` `sameItemContent()` / `sameItemList()` / `sameItemMultiset()` | 🚨`DesktopItem` **没有 `operator==`**，直接写 `QVector<DesktopItem> == QVector<DesktopItem>` 编译不过（C2678）；必须逐字段比 |
| C3 | `icongridwindow.cpp` `reorderItemInCategory()` | 盒窗口交换后补一次 `emit categoryChanged(QString())` → `requestSaveLayout`，让这次交换**即时落盘**（与 `handleTabDrop` 完全同款手法）。收纳盒窗口上该信号只连到 `requestSaveLayout`，**不回调 `setItems`**，所以不会把刚排好的顺序覆盖掉 |

## 四、为什么不改坏功能（等价性论证）

**核心不变式：每一条新路径都是"能省则省，不能省就退回原路径"，兜底永远是原行为。**

| 新路径 | 前置条件（任一不满足即 `return false`） | 不满足时 |
|---|---|---|
| `tryReorderInPlace` | 分类存在；非搜索态；非冻结态；盒视图要能找到该分类的盒子；网格视图要当前页正是该分类；每个条目都能命中唯一按钮且无剩余 | `rebuildGrid()` = 原行为 |
| `applyItemsDeltaInPlace` | 盒视图（`m_fencesMode \|\| m_boxView`）；非搜索态；非冻结态；分类键集合一字不差；变化分类 ≤ 4；每分类增删 ≤ 8；新旧路径交集 ≥ 一半 | `rebuildGrid()` = 原行为 |
| `FenceBox::applyItemsDelta` | 按钮集合与新条目**双向完全匹配**，否则 | `setItems()` → `rebuild()` = 原行为 |

补充保证：

- **接线零差异**：`createItemButton` / `createGridItemButton` 是唯一构造点，`rebuild` 与增量路径共用同一段 —— 不存在"新路径漏了某个信号"的可能。
- **不销毁按钮 ⇒ 不丢状态**：原地重排**不清选中**（`m_selection` / `m_anchor` 指针依然有效）、不进冻结、不动 `m_pageCacheHost` 里其它分类的缓存页。
- **分类页缓存签名自动对齐**：`parkCurrentGridPage()` 的签名取自**按钮自己的 `item()`**（按布局顺序），原地重排后布局顺序 = 新顺序 ⇒ 切走时记的是新签名，切回时 `adoptCachedGridPage` 比对当前数据 → **HIT**，不会被误判成过期。
- **顺序保护不掩盖真实变化**：`sameItemMultiset` 只挡"集合相同、仅顺序不同"；`scheduleDockItemsIntoBox` 那种"按位插入"是集合真变化，照收。

## 六、待你实机验证 / 本轮未做

**请你实机点一下**（GUI 交互层我无法驱动）：

1. 全屏收纳 → 盒内拖动一个图标到另一个图标的位置 → 松手应当**只是位置变了**，界面不闪、不重刷；
2. 从 Dock 拖一个图标进某个收纳盒 → 应当**只有那个盒子多出一个图标**，其它盒子完全不动；
3. 交换后切走分类再切回、以及关闭程序再打开 → 位置应当保持住（C3 的即时落盘）；
4. 顺带确认 F2 / Delete / 右键菜单 / 改名在盒内仍然正常（`createItemButton` 共用改动的回归点）。

**本轮刻意未做**（要你先拍板）：

- 网格视图（窗口化的主整理窗口）**未**做增量 —— 它本来就只重建"当前那一页"，收益有限而改动面更大；盒视图已覆盖你的两条诉求。
- `moveItemToCategory`（跨分类移动）仍是全量重建 —— 那是"集合真变"（一个分类 -1、另一个 +1），不在本次"交换位置"范围内。
