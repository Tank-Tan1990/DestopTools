## A 组｜系统级输入通道

### ✅ A1 合并低级键鼠钩子为进程级共享（4 个 → 2 个）
- **新增** `DestopTools/lowlevelhookmanager.h`（header-only 单例，`inline` 函数的局部 static 保证跨 TU 唯一，因此**无需改 .pro**）。
- **根因回顾**：`WH_KEYBOARD_LL` / `WH_MOUSE_LL` 是系统**同步回调到安装线程**的，Dock 与收纳盒各自安装了一套（key+mouse），全进程最多同时存在 4 个钩子 —— 每次鼠标移动都要走两遍本进程回调。
- **改法**：管理器全进程只装 1 个键盘钩子 + 1 个鼠标钩子，按注册顺序分发；语义与合并前逐条对齐：
  - 键盘消费者返回 `true` ⇒ 立即返回 1（吞键），后续消费者与前台程序都收不到；
  - 鼠标消费者无返回值（从不吞事件），全部消费者按序被通知；
  - `subscribe()` 对同一 token = 原地刷新回调 + `reinstall()`，保住原有「先卸后装」的自愈语义；
  - `suspend()/resume()` 嵌套计数：任一侧摘钩即全进程摘钩，两侧都恢复才装回。
- **改动点**
  - `desktopmirrorwindow.h`：删除 `s_hkKeyHook/s_hkMouseHook`；`hotkeyKeyHookProc/hotkeyMouseHookProc` → `hotkeyKeyConsumer/hotkeyMouseConsumer`。
  - `desktopmirrorwindow.cpp`：`ensureHotkeyHooks/releaseHotkeyHooks/suspendHotkeyHooks/resumeHotkeyHooks` 全部改走 `lowLevelHooks()`。
  - `icongridwindow.cpp`：`gridKeyHookProc/gridMouseHookProc` → `gridKeyConsumer/gridMouseConsumer`；`ensure/release/suspend/resumeGridHooks` 同上。
- **边界（有意的风险控制）**：内联重命名期间由 `dockiconbutton.cpp` / `desktopiconbutton.cpp` 临时安装的编辑期钩子**未纳入** manager —— 其生命周期只有秒级、逻辑独立（拦 Enter/Esc、点框外提交），纳入会显著抬高「重命名」这条核心功能的回归风险。因此编辑期短暂时为 2+2 个钩子（此前是 4+2）。
- **需回归**：Dock 与收纳盒上的 F2 / Delete / D 快捷键（含跨窗口拖动后立即按键、编辑框提交后再按键）。

### ✅ A2 DesktopImmunityFilter：HWND 分类缓存 + owner 自愈节流
- **根因**：全局 native event filter 对**每一条取出的消息**都跑完整判定（`GetWindowThreadProcessId` + 样式读取 + `isInputWindow`/`isDesktopWidget` 里的 `QWidget::find` + `qobject_cast`），而全屏 Dock 上 `WM_MOUSEMOVE/WM_NCHITTEST/WM_SETCURSOR` 每秒数百条。
- **改法**（`desktopimmunityfilter.h/.cpp`）：
  1. 新增按 HWND 的**分类缓存**（`KindExternal/KindChild/KindInput/KindDesktopWidget/KindPlainTopLevel`）：首次遇到该 HWND 才做完整判定，之后命中缓存即零系统调用、零 Qt 侧查找；
  2. `WM_DESTROY` 时清缓存（对话框等可重复创建的窗口不受影响）；
  3. 桌面挂件的 owner 自愈改为**节流复核**（300ms 内确认过就不再重复），期间绝大多数消息零开销通过；`WM_SYSCOMMAND` 始终不短路；
  4. 非挂件顶层窗在完成一次免疫后，除 `WM_SYSCOMMAND` 外直接早退（原语义本就是「一次后永久跳过」）。
- **语义不变**：输入窗口（内联编辑框 / 各类 QDialog）仍然完全不干预 —— 这是「F2/右键重命名首次后永久失效」的历史根因结论，未触碰。

### ✅ A3 qApp 事件过滤器改为按需挂载
- **根因**：`qApp->installEventFilter(this)` 常驻 —— 进程内**每个控件的每个事件**都要多走一次虚调用，而它实际只服务于「内联重命名期间点编辑框之外即提交」。
- **改法**：`onInlineEditStarted` 时 `installEventFilter`，`onInlineEditFinished` 时在所有按钮都不处于编辑态后 `removeEventFilter`（用独立标志 `m_appFilterInstalled`，异常时序下保守保留挂载 —— 宁可多留一次虚调用，也不漏提交）。

## B 组｜高频定时器

### ✅ B1 层级轮询 50ms → 150ms，并常态跳过 DWM 查询
- 本 tick 最贵的是对每个受保护窗口做**跨进程 `DwmGetWindowAttribute`**（走 DWM 代理）。原来 20Hz × 3 窗口 ≈ 60 次/秒。
- 现在：常态（可见且非最小化、且不在 show desktop 激活期）**每 5 拍（750ms）** 才做一次 DWM 兜底探测；只有「不可见 / 已最小化 / show desktop 激活期」才逐拍探测 —— 外壳隐藏必然同时让窗口变为不可见或最小化，不会漏恢复。

### ✅ B2 兜底压底 1000ms → 3000ms，且不可见即跳过
- `SetWindowPos(HWND_BOTTOM)` 没有「已到位就短路」的语义，每次都会让窗口管理器重算 z 序。
- **未采用**「`GetWindow(GW_HWNDNEXT)` 判是否已最底」：可靠判据需要从 Dock 沿 z 序向下枚举全部兄弟窗口并跳过 Progman/WorkerW/SHELLDLL_DefView，现实桌面上窗口数可达上百 —— 每拍 3 次 API × 上百比一次 `SetWindowPos` 更贵。改用「降频到 3s + 不可见即跳过」达到同一目的（代码注释已写明原因，留待将来需要时再细化）。

### ✅ B3 回收站状态轮询 1500ms → 9000ms
- `SHQueryRecycleBinW` 是 shell 命名空间查询，回收站条目多时单次可达数十毫秒，且它永远在跑。满/空图标翻转晚几秒刷新无感知损失。

### ✅ B4 图标异步加载：批 8→2、间隔 0ms→30ms
- 单图标首取要走 `IExtractIcon / SHDefExtractIcon / 系统镜像列表`，未命中缓存时 1~20ms；每拍 8 个 = 把事件循环钉住 40~160ms（启动期最明显）。降到 2 个后单拍上限约 40ms，配合 30ms 间隔，输入与绘制都有确定的响应窗口。

### ✅ B5 层级看护 500ms → 1000ms（5 处）
- `filesearchwidget.cpp` / `icongridwindow.cpp` / `todolistwindow.cpp` / `wallpaperwindow.cpp` / `shutdowntimerwindow.cpp`。被压住是低频事件，1s 检测延迟无体感差异。

### ✅ B6 DiagTrace 加开关（默认关闭）+ 落盘 80ms → 500ms
- **默认关闭**：关闭时 `log()` 立即返回 —— 不追加缓冲、不加锁，也**不会构造 Sink**（落盘定时器因此永不启动）。
- **开启方式（二选一）**：
  - 环境变量 `DESTOPTOOLS_DIAG=1`（启动前设置，临时排查最方便）；
  - INI（`%APPDATA%\DestopTools\DestopTools.ini`）写入 `[Diagnostics] traceEnabled=true`。
- 注意：默认关闭后 `DestopTools_trace.log` 不再增长；需要排查时按上述任一方式开启。

## C 组｜每次鼠标移动都在做的工作

### ✅ C1 拖动回收站命中：改为拖动开始一次性缓存 + 高亮节流
- **根因**：`onIconDragMove` 未节流 → 每像素重算：`recycleBinButton()` 对**每个** Dock 按钮调 `isRecycleBin()`（每次 2 次 QString 分配），`dragOverRecycleBin()` 对每个成员调 `isDeletableOnDrop()` → `ShellOps::isSafeToDelete()`（含 `QFileInfo::exists` 文件系统 stat + `QStandardPaths` shell 查询）。
- **改法**：
  1. 拖动开始（`onIconPressed` 组装拖动组后）一次性算好 `m_dragRecycleBin` 与 `m_dragDeletable`（与拖动组对齐的可拖删标志）；
  2. `dragOverRecycleBin()` 拖动中走缓存，只做纯几何相交；
  3. `updateDropTargetHighlight()` 节流到 40ms（与旁边的 `iconDragHoverChanged` 同款）；新增 `force=true` 参数供收尾/还原路径绕过节流，确保高亮确定性清除；
  4. `isRecycleBin()` 改为构造期算一次的成员 `m_isRecycleBinItem`（条目在按钮生命周期内不变）；
  5. `abortActiveDrag()` / `finishDrag` 清缓存。

### ✅ C2 网格 move 路径：去元属性查找 + 光标变化检测
- `m_dragSourceTab` 非空判断前置 —— 常态下它恒为空，于是每次鼠标移动省掉一次 `qobject_cast` 与一次 `property("isCategoryTab")` 的 QMetaObject 名字查找。
- `updateHoverCursor()` 加变化检测（`m_lastHoverCursorShape`）：边缘光标只在窗口最外圈 5px 内变化，绝大多数 move 目标形状与上次相同，而 `QWidget::setCursor()` 同值时不会短路。

### ✅ C3 FenceBox 悬停光标变化检测
- 用 `m_lastHoverCursorKey` 编码「默认 / 边缘缩放(N) / 标题栏移动」三种目标，只在变化时真正 `setCursor`/`unsetCursor`。

### ✅ C4 `allBoxWindows()` 返回缓存引用
- 原来每次调用都 `new` 一个 QVector 并逐个拷贝指针，而它在拖动悬停期间被反复调用。
- 改为返回内部缓存的 `const QVector&`，每次调用与「`m_boxes` 里非空的 window + `m_gridWindow`」**逐项比对**（盒数量通常个位数），不一致才重建 —— 因此**不需要任何「盒增删时置脏」的通知点**，天然不会漏更新（这是刻意避开的风险点）。

## D 组｜渲染层

### ❌ D1 分层窗整屏提交 —— **实测不成立，无需改架构**
已写最小基准程序（`tools/d1layer/`，`python tools/run_d1layer.py` 可复跑），实测「1 个 72×84 子控件 move 1px + repaint()」的平均每帧耗时：

| 窗口尺寸 | 子控件数 | 分层·整窗 | 不透明·整窗 | 分层·**局部** | 不透明·局部 |
|---|---|---|---|---|---|
| 640 × 480 | 28 | 0.713 ms | 0.735 ms | **0.058 ms** | 0.065 ms |
| 1280 × 720 | 84 | 2.216 ms | 2.271 ms | **0.058 ms** | 0.070 ms |
| 1920 × 1000 | 189 | 5.952 ms | 5.650 ms | **0.064 ms** | 0.078 ms |

**结论**：
1. **局部重绘的开销与窗口面积无关**（分层窗 0.058→0.064 ms，几乎不变；归一化数值随面积下降），说明 Qt 5.14 在 Windows 上对 `WS_EX_LAYERED` 的 flush **不会**把局部重绘放大为整窗 `UpdateLayeredWindow` 提交。**D1 的假设不成立，不需要改 Dock 的渲染结构。**
2. 「整窗 repaint」才贵（1920×1000 约 6 ms/帧），且**分层与不透明几乎一样贵** —— 说明这是 CPU 侧整窗重绘（绘制全部 189 个子控件）的成本，与分层无关。
3. **可执行推论**：拖动/悬停路径应始终保持**局部** `update(dirty)`，避免任何整窗 `repaint()`。现状已满足（框选用 `update(m_rubberRect)`、子控件 move 只产生局部脏区），无需改动。

### ✅ D2 DockIconButton 静态层（图标 + 标签）pixmap 缓存
- 把「向 QIcon 取位图 + 标签字体度量与二分截断」预渲染进一张 QPixmap；缓存键 = 设备像素尺寸 / 显示名 / 选中态 / 编辑态 / `QIcon::cacheKey()` / `QFont::key()`。
- hover 底、选中底、回收站提示环、拖动半透明**都不进入本层**，仍每次即时叠加 —— 因此不影响任何交互态外观（拖动半透明由外层 QPainter 的 opacity 统一施加）。
- 收益点主要在**标签的字体度量与二分截断循环**（原来每次重绘都跑一遍）。

### ⏸ D3 框选 16ms 轮询 —— 评估后按原建议**不动**
- 复核结果：`updateRubber()` 已有「`r == m_rubberRect` 就不重绘」判断，且只用 `update(dirty)` 局部重绘；`rubberTick` 仅在 `m_rubbering` 期间运行（`!m_rubbering` 即自停）。开销已可接受，不做改动。

## E 组｜钩子回调纪律

### ✅ E1 / ✅ E2 gate 判据重排 + 诊断日志开关短路
- **先说清一件事**：「回调只判按键 + 0ms 投递、把 gate 整体挪进事件循环」在**当前架构下做不到** —— 因为「这一键该不该吞（返回 1）」必须**同步**决定：若一律吞，在资源管理器里按 Delete 会被我们抢走；若一律不吞，收纳盒/Dock 的快捷键就永远失效。故 E1/E2 改为**消除回调内的重型操作**：
  1. **判据顺序重排**（各判据无副作用，AND 语义完全等价）：把 `m_selection.isEmpty()`、`s_hkLastClickOnDock`（Dock）/ `s_gridHot != this`（网格）这些 **O(1) 且最常见的拒绝原因前置**；把原本排在最前的 `isEditingAnyIcon()`（内含 `findChildren` 全量扫描 + QVector 分配）、`m_buttons` 全量遍历、`nativeHitTestIsDock`（Win32 命中测试）**移到最后** —— 只有「看起来真能响应」时才付这份代价。
  2. **日志短路**：新增 `DOCK_HK_TRACE` / `GRID_GATE_TRACE` 宏，`DiagTrace::enabled()` 为假时**连参数字符串都不构造**（`DiagTrace::log` 的实参是在调用点求值的，仅靠 `log()` 内部早退仍要白构造一遍 QString + arg 链）。这些判据点全在低级钩子回调路径上（回调超时会被系统静默摘钩），所以这层短路有意义。

## 建议验收顺序（体感优先）

1. **启动期**：双击 exe，观察启动过程中鼠标是否还发滞（B4 + A2 + A3 的收益）。
2. **拖动跟手度**：在 Dock 上拖动图标（含多选整组拖动）、拖到回收站上悬停 → 高亮是否正常、拖动是否顺滑（C1 + D2）。
3. **长时间运行**：放置 5~10 分钟，鼠标扫过桌面/Dock/收纳盒，观察是否有周期性「一顿一顿」（B1 + B2 + B3 + B5）。
4. **快捷键回归**：Dock 选中图标后 F2 / Delete；收纳盒内选中图标后 F2 / Delete；跨窗口拖动后立即按键；重命名（Enter / Esc / 点框外）—— 这是 A1 改动的重点回归面。
5. **Win+D / Win+M / 显示桌面**：三窗口仍应可见且不被最小化（B1 + B2 改动了恢复逻辑）。
6. **回收站**：清空/删除文件后，Dock 回收站图标应在 9s 内切换满/空。
