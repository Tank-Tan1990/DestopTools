## A 组｜系统级输入通道（决定性因素，建议优先）

### A1. 两个常驻 WH_MOUSE_LL 钩子挂在 GUI 线程 —— 全系统鼠标迟滞的根因
- 证据：`desktopmirrorwindow.cpp:2196-2197`（Dock 装 key+mouse 低级钩子）、`icongridwindow.cpp:105-106`（网格同样一套）
- 机理：`WH_MOUSE_LL` 是**系统同步回调到安装线程（本进程 GUI 线程）**的，**每一个原始鼠标输入事件（含移动）**都会回调一次；1000Hz 鼠标 = 1000 次/秒的跨线程同步往返。GUI 线程任何一次卡顿（一次重扫、一次整屏重绘、一次 shell 调用）都会**直接变成全系统光标迟滞**，因为鼠标输入在等我们返回。
- 加重因素：同时装了两套（Dock + 网格）→ 每次鼠标事件要走两遍。
- 现有缓解：`suspendHotkeyHooks / suspendGridHooks`（`desktopmirrorwindow.cpp:2183-2222`、`icongridwindow.cpp:96-121`）只在少数已知重活点生效（关闭、全量重扫），**覆盖不全**。
- 候选修法（按代价递增，可组合）：
  1. **合并为单一鼠标钩子**：一个进程级 HookManager 同时服务 Dock 与网格，钩子数 2→1；
  2. **把钩子移到专用线程**（自带消息循环），回调只写原子标志 + 投递消息，彻底切断「GUI 忙 → 全系统鼠标僵」的耦合；
  3. 把 `ensureHotkeyHooks()` 的调用点补全到所有可能的长任务外（治标）。
- 风险：中等（涉及 F2/Delete 时灵时不灵的旧坑，需回归测试）；收益：最大。

### A2. DesktopImmunityFilter 是全局 native event filter，且**每条消息**都做 6~10 次系统调用
- 证据：`main.cpp:30`（`a.installNativeEventFilter(&immunityFilter)`）、`desktopimmunityfilter.cpp:107-179`
- 逐条消息开销：
  - `:115` `GetWindowThreadProcessId`
  - `:129` `GetWindowLongPtrW(GWL_STYLE)`
  - `:136` `isInputWindow()` → `QWidget::find()` + `qobject_cast<QLineEdit*>` + `qobject_cast<QDialog*>`
  - `:138` `isDesktopWidget()` → 再一次 `QWidget::find()` + objectName 比较
  - `:142-143` `attachToDesktop()` → `GetWindowLongPtrW` + `IsWindow` + `GetClassNameW`
  - `:155-157` 又一次 `GetWindowLongPtrW`
- 触发频率：Windows 事件派发器对**每一条取出的消息**都跑一遍过滤器 —— `WM_MOUSEMOVE`、`WM_NCHITTEST`、`WM_SETCURSOR`、`WM_PAINT`、`WM_TIMER` 全在内。该文件自己的注释（`:40-41`）就写着「全屏 Dock 上鼠标移动每秒可产生数百条消息」。
- 候选修法：
  1. 首行加**消息类型白名单早退**（`WM_MOUSEMOVE/WM_NCHITTEST/WM_SETCURSOR/WM_PAINT/WM_TIMER/WM_GETOBJECT` 直接 `return false`，只有窗口创建/样式变更相关的 `WM_CREATE/WM_SHOWWINDOW/WM_STYLECHANGING/WM_SYSCOMMAND` 才走逻辑）；
  2. 用 `QHash<HWND, 分类>` 缓存「是否挂件 / 是否输入窗 / 是否已加样式」，命中即**零系统调用**（目前只有 DefView 查找被缓存，其它没有）。
- 风险：低；收益：高。

### A3. `qApp->installEventFilter(this)` —— 进程内每个事件都过一遍 Dock 的 eventFilter
- 证据：`desktopmirrorwindow.cpp:122`（装在 qApp 上）、`:2682-2704`（eventFilter 实现）
- 现状：move 事件只做一次类型比较就落到 `QWidget::eventFilter`，本身不重；但它是**进程级**过滤，所有控件（含上百个图标按钮）的**所有**事件都要虚函数走一遍。按下路径 `:2691-2699` 还会遍历 `m_buttons` 调 `isEditing()` / `editorJustOpened()`。
- 候选修法：把该守卫改为**仅内联重命名期间挂载/卸载**（编辑开始 install、结束 remove），与钩子同一生命周期；而非进程全程常驻。
- 风险：低；收益：中低。

## B 组｜高频定时器（周期性「一顿一顿」）

### B1. 50ms 轮询：每拍对每个受保护窗口做一次跨进程 DwmGetWindowAttribute
- 证据：`desktopmirrorwindow.cpp:591-598`（50ms）、`:646-653`（每拍每窗口 `IsWindow` + `DwmGetWindowAttribute(DWMWA_CLOAKED)` + `IsIconic` + `IsWindowVisible`）、`:629-639`（每 2.5s 再追加一轮 DWM 查询 + `GetWindowLongPtrW` + QString 拼接）
- 量化：20Hz × 3~4 个窗口 ≈ **60~80 次 DWM 同步调用/秒**（DwmGetWindowAttribute 要过 DWM 代理，单次亚毫秒到毫秒级），叠加在 GUI 线程上。
- 候选修法：
  1. 常态下 `IsWindowVisible(h) && !IsIconic(h)` 就**跳过** DWM 查询（斗篷只在被隐藏时才需要确认）——正常使用下直接省掉绝大部分调用；
  2. 间隔 50ms → 150~200ms（撤顶最多晚 150ms，肉眼不可辨）；
  3. 前台窗口类名没变就不查（事件驱动优先，钩子已覆盖 HIDE/CLOAK）。
- 风险：低（需回归 Win+D / 显示桌面）；收益：高。

### B2. 1s 兜底压底：无条件 `SetWindowPos(Dock, HWND_BOTTOM)`
- 证据：`desktopmirrorwindow.cpp:137-139`（1000ms 定时器）、`:412-423`（`parkAllTargetsAtBottom` 里无判断直接 SetWindowPos）
- 问题：**已经在最底层时也照写一次 z 序**，可能触发整屏分层窗口的合成/重绘 —— 若 D 组成立，这就是「每秒一次的整屏重绘」。
- 候选修法：写入前先看 `GetWindow(h, GW_HWNDPREV)` / 当前 z 序，已是最底则跳过；或间隔放宽到 3~5s。
- 风险：低；收益：中（若 D1 成立则高）。

### B3. 1.5s 一次 `SHQueryRecycleBinW`（shell 调用）
- 证据：`desktopmirrorwindow.cpp:144-146`（1500ms）、`:2427-2441`（pollRecycleBinState）、`shellops.cpp:140-149`（`SHQueryRecycleBinW`）
- 问题：shell 命名空间查询，单次可达毫秒~数十毫秒（回收站条目多时更慢），且**永远在跑**（哪怕回收站从没变过）。
- 候选修法：间隔 1.5s → 8~10s；或用 `SHChangeNotifyRegister` 监听回收站命名空间项（当前只监听桌面目录）。
- 风险：低；收益：中低。

### B4. 图标异步加载定时器 `interval(0)` + 每拍 8 个 Shell 图标
- 证据：`desktopiconbutton.cpp:285-311`（`s_iconTimer->setInterval(0)`、`batch = 8`）、`:313-317`、`:397-521`（首取图标走 IExtractIcon / SHDefExtractIcon / 系统镜像列表）
- 问题：0ms 定时器等于「事件循环一有空就跑」，每拍同步取 8 个图标（每个 1~20ms，未命中缓存时更久）→ 启动期/大目录刷新期，事件循环被切成 40~100ms 的阻塞块。**启动时鼠标卡**正是这个 + 首刷叠加。
- 候选修法：batch 8→2、interval 0→30ms；或把图标提取移到 `QThreadPool`（该改动大，需注意 `QPixmap` 只能在 GUI 线程构造）。
- 风险：低（仅影响图标出现速度）；收益：中高（启动期体感明显）。

### B5. 5 个长期窗各挂 500ms「层级看护」定时器
- 证据：`filesearchwidget.cpp:60-66`、`icongridwindow.cpp:2421-2430`、`todolistwindow.cpp:102-108`、`wallpaperwindow.cpp:107-113`、`shutdowntimerwindow.cpp:183-189`
- 现状：仅在窗口可见时运行，且 `ensureLayerAboveBandWindows()`（`desktopmirrorwindow.cpp:463-485`）内部会沿 z 序链遍历。窗口不重叠时开销不大。
- 候选修法：统一 500ms → 1000ms，并把「是否被压住」的判定简化为「先从 h 上溯遇到第一个非本进程窗口即停」。
- 风险：低；收益：低。

### B6. DiagTrace：80ms 定时器 + GUI 线程写文件
- 证据：`diagtrace.h:36-73`（80ms `flush()`，有内容时 `QFile::open/write` 落盘）、调用点在热路径上（`desktopmirrorwindow.cpp:2150` `hotkeyAction`、`icongridwindow.cpp:673-692` gate 的每一条 FAIL 分支）
- 问题：12.5 次/秒的互斥锁（可忽略），但**一旦有内容就在 GUI 线程做文件 I/O**（`DestopTools_trace.log` 无大小上限，只增不减）。
- 候选修法：加一个「诊断开关」QSettings key，默认关闭时不启动定时器、`log()` 直接返回；或落盘间隔放宽到 500ms。
- 风险：低；收益：低。

## C 组｜每次鼠标移动都在做的工作（跟手度）

### C1. Dock 拖动中**每一次 move** 都重算「是否压在回收站上」——含文件系统 stat 与 shell 路径查询
- 证据链：
  - `dockiconbutton.cpp:498` `emit dragMove(this)`（逐像素触发）
  - `desktopmirrorwindow.cpp:2395-2404` `onIconDragMove` → **未节流**直接调 `updateDropTargetHighlight()`
  - `:2464-2472` `updateDropTargetHighlight()` → `recycleBinButton()`（遍历全部按钮）+ `dragOverRecycleBin()`
  - `:2447-2462` `dragOverRecycleBin()` → 对拖动组**每个图标**调 `b->isDeletableOnDrop()`
  - `dockiconbutton.cpp:322-329` `isDeletableOnDrop()` → `ShellOps::isSafeToDelete()`
  - `shellops.cpp:151-170`：`QFileInfo::exists()`（**文件系统 stat**）+ 3× `QDir::fromNativeSeparators` + `QStandardPaths::writableLocation(DesktopLocation)`（**shell 查询**）
  - `dockiconbutton.cpp:315-320` `isRecycleBin()` 每次调用产生 2 次 QString 分配（`.trimmed().toLower()`），而它被 `recycleBinButton()` 对**每个**按钮调用
- 量化（100 个图标、拖 1 个）：每次鼠标移动 ≈ 200 次 QString 分配 + 1 次 stat + 1 次 shell 路径查询 + 一次可能的 repaint/`raise()`。
- 候选修法：
  1. 拖动开始（`onIconDragStart`）时**一次性**算出：回收站按钮指针 + 拖动组的「可删除」布尔集合，move 期间只用缓存；
  2. `updateDropTargetHighlight()` 节流到 40ms（与 `iconDragHoverChanged` 同款，旁边代码已经这么做了）；
  3. `isRecycleBin()` 改为构造期算一次的成员 `bool`。
- 风险：低；收益：高（拖动跟手度直接改善）。

### C2. 网格：每次鼠标移动都走 eventFilter 的 `qobject_cast` + 元属性名查找 + `setCursor`
- 证据：`icongridwindow.cpp:2731-2740`（`enableChildMouseTracking` 递归给**所有子控件**装 eventFilter，含每个图标/标签）、`:2872-2890`（MouseMove 分支：`qobject_cast<QToolButton*>` → `btn->property("isCategoryTab")` 元属性名查找 → `w->mapTo()` → `updateHoverCursor()`）、`:2725-2729`（`setCursor(resizeCursorShape(...))`，**无变化检测**）
- 问题：鼠标扫过收纳盒/网格时，每个 move 都做一次元属性名查找 + 一次 `setCursor`（Qt 5.14 `QWidget::setCursor` 未见同值短路）。
- 候选修法：① `m_dragSourceTab` 为空时直接跳过属性查找（现在是先查属性再比较指针，顺序反了）；② `setCursor` 前先比较目标形状，变了才设。
- 风险：低；收益：中。

### C3. FenceBox 悬停：每次 move 都 `setCursor()` / `unsetCursor()`
- 证据：`fencebox.cpp:389-393`（`if (edges != Qt::Edges()) setCursor(...); else if (...) setCursor(...); else unsetCursor();` 全在 move 路径里，无变化检测）
- 候选修法：同 C2-②，记录上一次的光标状态。
- 风险：低；收益：中低。

### C4. 拖动悬停解析：每次分配 QVector + 遍历全部盒窗口
- 证据：`mainwindow.cpp:954-956`（`onDockIconDragHover`）、`:906-913`（`allBoxWindows()` 每次 `new` 一个 QVector）、`:934-945`（`resolveBoxAt` 遍历）
- 现状：已被 40ms 节流（`desktopmirrorwindow.cpp:2408-2414`），可接受。
- 候选修法：`allBoxWindows()` 改返回缓存的 `const QVector<IconGridWindow*>&`，盒增删时重建。
- 风险：低；收益：低。

## D 组｜渲染层（大面积重绘）

### D1. 整屏 `WA_TranslucentBackground` 分层窗：局部重绘可能触发整屏合成（**待实测确认**）
- 证据：`desktopmirrorwindow.cpp:112`（`WA_TranslucentBackground`）+ `:2779-2790`（showEvent 里铺满主屏 geometry）；网格全屏收纳模式同理
- 疑点：Qt 对分层窗（WS_EX_LAYERED）的 flush 走 `UpdateLayeredWindow` 提交**整个窗口表面**（Windows 的实现按窗口尺寸提交），1080p≈8MB / 4K≈33MB；果如此，则拖动图标时**每 move 一次 move() + repaint** 都会附带一次整屏 alpha 合成。
- 候选修法（若实测成立）：① 拖动/悬停重绘节流到 16ms（合并同一帧内的多次 move）；② 或 Dock 改为「自绘壁纸 + `WA_OpaquePaintEvent`」，不再用分层透明。
- 说明：这一条我**没有直接证据**（Qt 源码未安装，无法查 flush 实现）。如果您同意，我可以写一个 40 行的最小基准程序（整屏半透明窗 + 72×84 子控件逐帧 move，计时）来证伪/证实，再决定动不动它。
- 风险：改动大；收益：若成立则很高。

### D2. DockIconButton 每次重绘都取 QIcon 位图 + 标签双绘
- 证据：`dockiconbutton.cpp:374`（`m_icon.pixmap(pmSize, pmSize)`）、`:411-426`（标签画两遍：1px 阴影 + 白字）
- 现状：`QIcon` 内部有按尺寸的缓存，成本可控；拖动态 `:344` 用 `p.setOpacity()` 整体半透明。
- 候选修法（可选）：把「图标 + 标签」在尺寸/选中态变化时预渲染进 `QPixmap` 缓存，hover/选中只叠一层底。
- 风险：低；收益：低。

### D3. 框选橡皮筋 16ms 轮询
- 证据：`desktopmirrorwindow.cpp:1952-1958`（16ms）、`:1984-1992`（`rubberTick` 读 `QCursor::pos` + `GetAsyncKeyState`）、`:1961-1970`（只在 rect 变化时 `update(dirty)`）
- 现状：仅框选期间运行，且有「位置没变就不重绘」的判断。可接受，**建议不动**。

## E 组｜次要 / 纪律风险（不直接导致卡顿，但同源）

### E1. 键盘钩子回调里做完整上下文判定（含 `findChildren` 全量扫描）
- 证据：`icongridwindow.cpp:230-242`（钩子回调里循环调 `hotkeyGateOk()`）、`:671-696`（gate → `isEditingAnyIcon()`）、`:652-661` + `:600-610`（`allIconButtons()` 用 `findChildren` 递归扫描并分配 QVector）
- 问题：违反「低级钩子回调只投递 0ms 请求」的纪律；F2/Delete 连击时每次都要全量扫控件树。若某次超时（>300ms）钩子会被系统静默摘除 —— 这正是项目已知的「F2 用一次就失效」同源坑。
- 候选修法：回调只判「按键 + 0ms 投递」，把 gate 判定整体挪进事件循环（与 Dock 侧 `hotkeyAction` 保持一致做法）。
- 风险：低；收益：低（但可消除一类隐患）。

### E2. Dock 侧 `hotkeyAction()` 在钩子回调内做全量 gate + 写诊断日志
- 证据：`desktopmirrorwindow.cpp:2147-2178`（`hotkeyAction` 内调 `hotkeyContextOk()`：`GetCursorPos` + `nativeHitTestIsDock`（`GetWindowRect`/`WindowFromPoint`/`GetClassNameW`）+ 5 次 `GetAsyncKeyState` + 遍历 `m_buttons` + `DiagTrace::log`）
- 候选修法：与 E1 合并处理（回调只投递）。
- 风险：低；收益：低。
