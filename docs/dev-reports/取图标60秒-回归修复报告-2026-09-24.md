# 「取图标要 60s 以上」回归修复报告

- 日期：2026-09-24
- 现象：切换/刷新分类页后，整页图标长时间停在占位图，几十秒后才慢慢「冒」出来
- 用户要求：**「之前的方式是加载缓存，请恢复」**
- 结论：**确认是我 2026-09-24「6 条修复方向」那一轮引入的回归**。已修复并验证。

---

## 一、先证明「不是取图本身慢」

在动手之前先排除了"Shell 取图慢"这个最容易被误认的方向。

用 ctypes 复现 `loadIcon()` 的全部取图路径（`SHDefExtractIconW` / `SHParseDisplayName`+`SHGetFileInfoW` /
`SHGetFileInfoW(SHGFI_ICON)`），对用户 **Unity 分类里的全部 51 个真实项**逐个计时
（路径取自 `%APPDATA%\DestopTools\categories.ini`）：

| 项 | 结果 |
|---|---|
| 项数 | 51（全部存在） |
| 整页冷取合计 | **578 ms** |
| 平均 | **11.3 ms/项** |
| 最慢单项 | 40.1 ms（`Unity 2022.3.62f3c1.lnk`） |

> 这批项里绝大多数是 `*.unitypackage`（117MB / 128MB / 105MB…），本来是最可能触发第三方
> 压缩扩展解析的类型，实测依然只有 1.8~1.9 ms（`SHDefExtractIcon` 返回 `S_FALSE` 不受理，走兜底）。

**结论：整页一次性冷取只要 0.58 秒，且缓存命中时单次 ≈0 ms。60 秒绝不可能是取图本身造成的。**

## 二、根因（三条，全部是我上一轮引入的）

### 根因 1｜缓存命中也要排队 —— 最关键

`DesktopIconButton` 构造函数末尾是**无条件** `queueIconLoad(this)`：

```cpp
// 修复前
queueIconLoad(this);   // 构造函数末尾入队，等待事件循环空闲时取真实图标
```

于是**即使这张图早就在进程内缓存 `g_iconCache` 里**，也必须排进 30 ms 一拍的队列、
等定时器轮到才会 `setIcon`。用户看到的正是「整页占位图标迟迟不消失」。

这直接违背了用户说的「之前的方式是加载缓存」——**缓存命中的语义就是"立刻出图"，
不该再经过任何队列**。

### 根因 2｜让拍阈值 = 时间预算，正常项被误判成"长尾"

上一轮我加的长尾治理：

```cpp
const qint64 kIconProcessBudgetMs = 20;
if (s_lastBurstMs > kIconProcessBudgetMs) { s_lastBurstMs = 0; return; }   // 让出整拍
```

`s_lastBurstMs` 是**上一拍整轮循环**的耗时。正常冷项 11.3 ms/项 ⇒ 一拍处理 2 项 = 22.6 ms
⇒ **22.6 > 20 成立** ⇒ 下一拍整体让出。于是变成「干活一拍、空转一拍」，
**处理速度直接砍半**；冷项越多越明显。

Dock 侧同一个错误更极端：`kIconBurstBudgetMs = 12`，与让拍阈值是**同一个常量**，
11.3 ms 的项连来两个必触发让拍。

> 让拍只该为**真正的长尾**（数百 ms）而设。用"一帧大小的预算"当让拍阈值，
> 等于把"长尾保护"退化成"半数拍空转"。

### 根因 3｜闸门加在了整个队列入口，把缓存命中一起拦了

```cpp
void DesktopIconButton::processIconQueue() {
    if (ForegroundGate::fullscreenActive()) return;   // ← 整拍直接返回
    if (s_lastBurstMs > kIconProcessBudgetMs) { ... return; }
```

设计意图是"全屏 / 撞长尾时不做 **Shell 查询**"。但这两道判断放在了函数**最开头**，
于是连**只读哈希表、零 Shell 调用**的缓存命中项也被一起拦下。
全屏误判或长尾连发时，队列等于停摆。

## 三、修复

### 1. 新增「缓存优先」快路径（兑现用户要求）

`desktopiconbutton.h` — 新增私有方法：

```cpp
// 只查进程内图标缓存（零 Shell 调用）：命中即同步 setIcon 并返回 true。
bool trySetIconFromCache();
```

`desktopiconbutton.cpp`：

```cpp
bool DesktopIconButton::trySetIconFromCache() {
    if (!m_item.icon.isNull()) { setIcon(m_item.icon); return true; }
    const QIcon cached = DesktopScanner::cachedIcon(
        m_item, m_iconPx, Theme::shortcutArrowOverlayScale(m_arrowScale));
    if (cached.isNull()) return false;      // 冷项：交给异步队列走 Shell
    m_item.icon = cached;
    setIcon(cached);
    return true;
}
```

三处调用点全部改为「先查缓存，未命中才入队」——与 Dock 侧 `setDockButtonIcon` 同构：

| 位置 | 触发场景 |
|---|---|
| 构造函数 | 新建按钮（重建 / 切分类 / adopt 装回） |
| `setViewMetrics()` | 大 / 中 / 小图标档切换 |
| `setShortcutArrowScale()` | 收纳盒把箭头系数设为 2.0 |

> `setShortcutArrowScale()` 由 inline 赋值**改为函数**：`arrowScale` 是缓存键的一部分，
> 构造时按 1.0 取到的图在改成 2.0 后必须作废重取（否则角标尺寸不对）。
> 调用时序 `构造(1.0) → setShortcutArrowScale(2.0) → setViewMetrics(真实 px)` 三步
> 都只做「清旧图 + 查缓存/入队」，最终一定落在 `(真实 iconPx, 2.0)` 这一组合上。

### 2. 队列重写：两类任务分开处理

```cpp
void DesktopIconButton::processIconQueue() {
    QElapsedTimer burst; burst.start();
    const bool letGo   = (s_lastBurstMs > kIconLetGoMs);      // 只有真长尾才让拍
    const bool blocked = ForegroundGate::fullscreenActive();

    while (!s_iconQueue.isEmpty()) {
        QPointer<DesktopIconButton> btn = s_iconQueue.takeLast();
        if (!btn) continue;

        // ① 缓存命中：零 Shell 调用 ⇒ 无条件放行，也不消耗预算
        if (btn->trySetIconFromCache()) { btn->m_iconQueued = false; continue; }

        // ② 冷项遇到闸门/让拍：放回队列尾部并收手（本拍 s_lastBurstMs≈0 ⇒ 下拍必为 false，不会自锁）
        if (blocked || letGo) { s_iconQueue.append(btn); break; }

        btn->m_iconQueued = false;
        btn->loadIconNow();
        if (burst.elapsed() >= kIconProcessBudgetMs) break;
    }
    s_lastBurstMs = burst.elapsed();
    if (s_iconQueue.isEmpty() && s_iconTimer) s_iconTimer->stop();
}
```

- 缓存命中 → **整页在同一拍内铺满**，不吃预算、不受全屏闸门/让拍限制
- 真冷项 → 才受两道限流（全屏让路 = 暂停而非丢弃；到预算收手）

### 3. 让拍阈值独立（两侧）

| 位置 | 常量 | 修复前 | 修复后 |
|---|---|---|---|
| `desktopiconbutton.cpp` | 让拍阈值 | 20 ms（= 预算） | **`kIconLetGoMs = 60`** |
| `desktopmirrorwindow.cpp` | 让拍阈值 | 12 ms（= 预算） | **`kIconLetGoMs = 60`** |
| `desktopmirrorwindow.cpp` | 单拍预算 | 12 ms | 12 ms（不变） |

## 四、「没破坏现有功能」的证明

1. **全部改动是控制流增补**：没有删除/改写任何既有函数语义、数据格式、配置键、菜单项。
2. **稳态路径逐字节一致**：前台非全屏 + 桌面无变化时，三条新判据（全屏门 / 让拍 / 缓存优先）
   中前两条不触发；缓存优先路径的产物与旧实现 `loadIcon` 命中缓存后的结果**是同一份 `QIcon`**。

## 六、预期效果与复验方法

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 切分类 → 切回（缓存已热） | 排队逐个出图 | **同一拍瞬间铺满** |
| 大/中/小图标档来回切 | 排队 | **瞬间**（同尺寸早已缓存） |
| 进程首次启动、冷缓存 | 整页 ~0.58 s（分拍） | 同左（本来就该走 Shell） |
| 全屏期间 | 队列整体停摆 | 缓存命中照常出图，冷项让路 |

**复验**：打开分类页 → 切换分类来回几次 → 图标应**立即**全部到位（约 30 ms 内），
不再逐个「冒」出来。首次冷启动（刚开程序、该分类图标从未取过）仍会有约 0.6~1 s 的
分拍填充，这是正常的 Shell 取图，与本次回归无关。

## 七、附：定位过程中排除的项（带证据，避免重复挖）

| 怀疑 | 结论 |
|---|---|
| `clearIconCache()` 被反复调用 | **否**。全项目仅 2 处调用，都是「切换快捷方式箭头开关」时才触发 |
| 单张 Shell 取图慢 | **否**。51 项实测平均 11.3 ms/项、整页 578 ms |
| `suffixMismatchesContent()` 对带点的文件夹名误判 | **否**。它只对魔数表内类型（jpg/png/zip/…）嗅探，`unitypackage`/`def`/`kage` 均不在表内 |
| 磁盘图标缓存被删 | **否**。项目从来只有进程内 `g_iconCache`（`QHash<QString,QIcon>`），无持久化缓存 |
| 全屏闸门误判为真 | **否**。沙箱内用 ctypes 复现同一套判据实测 `SHQueryUserNotificationState=5`、前台不覆盖 `rcMonitor` ⇒ `False`（不过本次已顺带修掉了"全屏时连缓存命中也拦"的过激行为） |
| `mainwindow.cpp` / `fencebox.cpp` 被改坏 | **否**。本轮及上一轮均未改动这两个文件 |
