## 二、B1 为什么是"卡死 2~3 秒"的正靶心

报告《三项检查》里的结论是"**扳机 = 桌面变化后 `refresh()` 在 GUI 线程上跑的整屏 Shell 查询**"，但当时没能拆到最小单元。这次拆开了：

```
SHChangeNotify → 250ms 防抖 → refresh()
    └─ readEntries() → DesktopScanner::scan() → makeItem()（每个桌面项一次）
                                                    └─ 若 .lnk → resolveShortcut()
```

而 `resolveShortcut()` 原先**完全没有缓存**，每个 `.lnk` 每次刷新都要走一整轮 COM：

```
CoCreateInstance(CLSID_ShellLink)   ← 加载 COM 服务器
  → IPersistFile::Load(linkPath)    ← 读盘
    → IShellLink::GetPath(...)      ← 求解目标，可能再触达目标所在卷
```

桌面有几十个 `.lnk` ⇒ **每次 `refresh()` 就是几十次完整 COM 往返，全部发生在 GUI 线程**。机械盘 + 360 抢盘时单次可达数十~数百 ms（《三项检查》实测单次 Shell 调用最慢 **485 ms**、今日 19:52 复测最慢 **45.8 ms**），几十项叠加正是"2~3 秒"的量级。

而常驻的 `WH_KEYBOARD_LL` 把这段阻塞**同步放大**：低级钩子是系统同步回调到安装线程（GUI 线程）的，**GUI 线程不空闲，全系统键鼠就一起等**。

⇒ 修掉 `resolveShortcut` 的重复 COM 解析后，稳态刷新退化为「2 次目录枚举 + N 次 stat + O(1) 哈希查找」，量级下降一到两个数量级。
