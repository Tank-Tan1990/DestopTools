## 一、用户现象

> 程序启动时，dock 中的文件图标会进入 F2 重命名的状态；而且多个文件的话，需要鼠标点击 dock
> 多次，才能全部消除重命名状态。

## 二、取证（先看现场，不猜）

| 证据 | 结果 |
|---|---|
| 真实桌面目录（注册表 `User Shell Folders\Desktop`） | 被重定向到 **`F:\Desktop`**（不是 `%USERPROFILE%\Desktop`） |
| `F:\Desktop` 中命中「新建 / New 」命名的条目 | **恰好 3 个**：`新建文本文档 (2).txt`、`新建文本文档 (3).txt`、`新建文本文档 (4).txt` |
| 该目录总条目 | 167 |

3 个文件 ↔ "点多次才能全部消除" —— 数量级完全吻合，链路可解释（见下）。

## 三、根因

**判据用的是"名字像新建"，不是"本次会话内新建"。**

1. 自动弹框的唯一来源：`refresh() → layoutButtons()` 内的
   `if (isNewlyCreatedName(e.displayName) && !m_autoRenamedPaths.contains(key))` →
   `m_autoRenameQueue.insert(key)` → `QTimer::singleShot(0, …, applyAutoRename)`。
2. `isNewlyCreatedName()` 是**纯名字启发**：
   ```cpp
   return name.startsWith(QStringLiteral("新建")) || name.startsWith(QLatin1String("New "), Qt::CaseInsensitive);
   ```
   对桌面上**真实存在**的 `新建文本文档 (3).txt` 永远成立 —— 它与"刚建出来还没改名"的那一个
   名字完全同形，**收紧正则也无法区分**。
3. `m_autoRenamedPaths`（"已弹过、别再弹"集合）是**纯内存** `QSet`，**不落盘** →
   每次程序启动都是空集 → 启动首轮扫描就把桌面上 3 个遗留文件全部判成"新建项"并入队。
4. `applyAutoRename()` **一次只弹一个编辑框**（`if (opened) break;`），且要在
   `onInlineEditFinished()` 里被"提交/取消"后才 `singleShot(0, …applyAutoRename)` 弹下一个
   → 于是"有几个这样的文件，就要点几次 dock 才能全部消掉"。

一句话：**没有任何机制区分"启动时桌面上已经有的"和"本次会话里刚新建的"**，而名字启发对前者恒真。

## 四、修法（1 个成员 + 1 段块）

判据换成**事实**：程序启动后首次拿到**有效**桌面条目时，把此刻已存在的一切登记为
"本次会话之前就存在"，它们永不自动弹框。

`desktopmirrorwindow.h`：

```cpp
// 🚨会话基线是否已登记（只做一次）：程序启动后首次拿到有效桌面条目时，把此刻已存在的一切
// 记入 m_autoRenamedPaths —— "本次会话之前就存在"的项永不自动弹重命名框。
bool m_autoRenameArmed = false;
```

`desktopmirrorwindow.cpp` → `refresh()`，紧邻 `layoutButtons()` **之前**：

```cpp
if (!m_autoRenameArmed) {
    m_autoRenameArmed = true;
    for (const Entry& e : m_entries)
        m_autoRenamedPaths.insert(QDir::fromNativeSeparators(e.shellPath).toLower());
}
layoutButtons();
```

要点：

- **位置刻意放在 `NativeListView` 就绪判定之后**：`refresh()` 里更早有一处
  `if (m_sourceMode == NativeListView && m_entries.isEmpty() && !bestListView()) { 500ms 后重试; return; }`。
  若把基线块放到它前面，首轮扫描为空时会把基线记成**空集** → 等于没修（这正是"看起来修了、
  重启还在弹"的典型陷阱）。
- **循环登记全部 `m_entries`（含被收纳盒收走的隐藏项）**：隐藏项在布局循环里被
  `if (m_hiddenShellPaths.contains(...)) continue;` 提前跳过，若只在入队处打标记就会漏掉它们，
  日后从收纳盒拖回 Dock 时会突然弹框。
- **两条入队路径同时覆盖**：`layoutButtonsGrid()`（DesktopOrganize 源）与
  `layoutButtonsNative()`（NativeListView 源，含其内部 `createButton` lambda）—— 判据都在同一处
  集合 `m_autoRenamedPaths`，一处生效即两处生效。

# 八、追加：Dock 内新建文件 → 自动进入重命名态（**已确认保留**，01:55 用户复核）

用户口径：「如果我在 Dock 中新建一个文件，自动进入重命名状态功能要保留。」

**结论：保留，且与本次修复不冲突** —— 因为新逻辑用的判据是"**本次会话内新增**"这个事实，
而"刚在 Dock 里新建出来的文件"**必然**不在会话基线里，走的是原路径。

## 8.1 逐环核对（读码取证，未代跑程序）

| 环节 | 代码位置 | 结论 |
|---|---|---|
| Dock 空白处右键 → 原生 Shell 桌面菜单 | `mousePressEvent()` 空白分支：`m_menuOpen = true; showDesktopEmptyMenu(globalPos); m_menuOpen = false; flushPendingRefresh();` | 菜单是 `TrackPopupMenu` 原生模态循环，期间刷新被 `m_menuOpen` 挡住（**必须挡**：循环内重建按钮会让随后弹出的重命名框挂到已销毁按钮上） |
| Shell「新建 → 文本文档」 | `showDesktopEmptyMenu()` 内 `pcm->InvokeCommand(...)` | 文件落到**真实桌面**（本机即 `F:\Desktop`）→ `SHChangeNotify` → 刷新 |
| 菜单关闭 → 补做刷新 | `flushPendingRefresh()` → `refresh()` | `m_entries` 多了一项 ⇒ SHA1 指纹变化 ⇒ **不会**走 `refresh:unchanged-skip` 早退 |
| 会话基线 | `if (!m_autoRenameArmed)` 块 | `m_autoRenameArmed` 在启动首轮已置 true ⇒ 本轮**跳过**，不会把新文件误登记成"既有" |
| 入队 | `layoutButtons()` 内 `isNewlyCreatedName(displayName) && !m_autoRenamedPaths.contains(key)` | 新 key **必不在**集合里（基线只装了"启动那一刻已存在"的路径）⇒ 入队 |
| 弹框 | `singleShot(0, applyAutoRename)` | 一次弹一个；提交/取消后由 `onInlineEditFinished` 继续弹下一个（连续新建多个不漏弹） |

**判据正交性**：`isNewlyCreatedName()`（名字形状：`新建…` / `New …`）负责"认出这是 Shell 刚建出来
还没改名的默认名"；`!m_autoRenamedPaths.contains(key)`（会话事实）负责"排除本来就存在的老文件"。
两者是**与**关系，各管一段 —— 删掉任何一个都会坏（删前者：改名后按 F2 也自动弹；删后者：本 bug 复现）。

## 8.2 项目内不存在第二套新建实现

全项目 grep `createNewFile / createNewFolder / 新建文件 / 新建文件夹 / createFile / CreateDirectory`
→ **仅 1 处命中**：`desktopmirrorwindow.cpp:1225` 的一句注释（讲"新建与刷新竞态"）。
即：**新建一律走原生 Shell 菜单**，没有旁路会绕开上述链路，也没有第二处需要同步改的地方。
