# 游戏（War3）运行期间鼠标偶发卡死 2~3 秒 —— 成因分析报告

- 日期：2026-09-24
- 对象：`DestopTools.exe`（Qt 5.14.2 / MSVC2017_64 release，PID 2112，本次分析时正在运行）
- 约束：**本次未修改任何功能代码**，只做取证与实测
- 结论一句话：**卡死的"开关"是全局低级键盘钩子（GUI 线程被钉住 → 全系统输入链等待），
  "扳机"是每次桌面变化后刷新时在 GUI 线程上跑的整屏 Shell 查询（本机 5 ms/项、最慢 485 ms/项），
  "放大器"是完全机械硬盘 + 360 主动防御在游戏读盘期间的资源争抢。**

---

## 一、先说结论：这是一个「三重叠加」而不是单一 bug

| 层次 | 角色 | 事实 |
|---|---|---|
| **放大器** | 全局低级键盘钩子 `WH_KEYBOARD_LL` | 低级钩子是**系统同步回调到安装线程（本程序 GUI 线程）**的。只要 GUI 线程被钉住，**键盘与鼠标输入一起**在等我们返回；超过 `LowLevelHooksTimeout`（本机未改注册表，= 系统默认 **300 ms**）系统就不再等 |
| **扳机** | 桌面变化 → `refresh()` 在 GUI 线程跑整屏 Shell 查询 | 本机实测 **5.15 ms/项**，204 项 ≈ **1.05 秒**；最慢单项 **56.9 ms**，历史上出现过 **485 ms**（`360DesktopLite64.exe.lnk`） |
| **放大器** | 图标队列 30 ms/个 + 机械硬盘 + 360 | 一轮刷新把工作量摊成 **≈6 秒**的连续卡顿窗口；游戏读盘时单次 5 ms 变几十~几百 ms |

三者都不是"2~3 秒"级，但**叠起来**就是：游戏读盘 → 机械盘寻道排队 → 我们某一拍 Shell 查询从 5 ms 涨到数百 ms，
甚至几秒 → 钩子回调被拖住 → **全系统鼠标/键盘冻结**（这正是"鼠标卡死 2~3 秒"的观感）。

## 三、成因逐条（按"对 2~3 秒卡死"的贡献度排序）

### ① 【放大器·必要条件】全局低级键盘钩子把「GUI 线程任何卡顿」放大成「全系统输入冻结」

- **位置**：`lowlevelhookmanager.h:141` — `SetWindowsHookExW(WH_KEYBOARD_LL, ..., mod, 0)`
- **事实**：鼠标侧已改 Raw Input（异步，`rawmouse.h`），**但键盘侧仍是 `WH_KEYBOARD_LL`**，
  且它只要还有消费者（F2 重命名 / Delete 删除）就**常驻安装**。
- **机理**：低级钩子由系统**同步回调到安装线程**——系统的输入处理线程会把消息投给我们的 GUI 线程并**等它返回**；
  在等待期间，**鼠标原始输入也不会被继续派发**（输入处理是单一通路）。GUI 线程被钉住多久，光标就僵多久。
- **阈值**：`LowLevelHooksTimeout` 本机未改（默认 **300 ms**）。超过后系统不再等（钩子会被静默摘除，
  这也正是项目已知的"F2 用一次就失效"的同源坑）。
- **结论**：**这一条不产生卡顿，但把下面任何一条的"几十毫秒"变成用户能感觉到的"卡死"**。
  没有这条，②③⑥ 只会表现为"偶尔发涩"。

### ② 【扳机·最高嫌疑】桌面变化 → `refresh()` 在 GUI 线程跑整屏 Shell 查询

- **位置**：`desktopmirrorwindow.cpp:819 void refresh()` → **L825 `readEntries()`**，而内容指纹早退在 **L872**。
  ⇒ **指纹只能省掉"重建按钮"，扫描/查询每次都跑。**
- **路径**：Dock 实际使用 `SourceMode::NativeListView`（`mainwindow.cpp:242`），
  `readEntriesFromListView()`（`:1148`）会做：`buildNameMap()` + 逐项 `effectiveTarget()`
  （`IShellLink` 解析，`desktopscanner.cpp:540`）+ 图标提取（`SHGetFileInfoW`，`desktopscanner.cpp:506/573`）
  + 快捷方式角标 `SHGetFileInfo(SHGFI_LINKOVERLAY)`。
- **本机实测**：逐项 Shell 查询 **5.15 ms**，204 项 ≈ **1.05 秒**；**长尾极严重**：
  最慢单项 56.9 ms，抽样中 `360DesktopLite64.exe.lnk` 达到 **485 ms**。
- **触发源**：`SHChangeNotifyRegister`（`desktopmirrorwindow.cpp:3340`，范围 = `CSIDL_DESKTOP` = `F:\Desktop`，
  非递归，含 `SHCNE_ASSOCCHANGED`）→ 250 ms 防抖 → `refresh()`。
  **任何程序在桌面根目录新建/改名/删除/改属性文件都会触发。**
- **为什么游戏时最严重**：游戏把机械盘读写打满 → Shell 查询要读图标资源/解析快捷方式 → 5 ms 变几十~几百 ms。
- **结论**：这是"卡死 2~3 秒"的**扳机**，也是唯一能解释"为什么是秒级而不是毫秒级"的路径。

### ③ 【放大器】图标队列以 30 ms/个的节奏在 GUI 线程续跑，把 1 秒的活摊成 6 秒的持续卡顿窗口

- **位置**：`desktopiconbutton.cpp:296 s_iconTimer->setInterval(30)`；`processIconQueue()` `batch = 1`（`:310`）
- **事实**：每次刷新会重建 204 个图标按钮 → 队列 204 项 → 以 30 ms 一拍、每拍 1 个推进
  ⇒ **连续 ≈6 秒**内，每 30 ms 就有一次"在 GUI 线程做 Shell 取图"。
- **后果**：这 6 秒内**任意一拍**撞上长尾项（56~485 ms，或游戏读盘时的秒级项），
  该拍就把钩子回调拖住 → 冻结。**这解释了"有时候"——取决于是否恰好撞上慢项。**
- 注：代码注释（`:303-309`）已把 batch 从 8 降到 1，方向正确，但**没有消除长尾**。

### ④ 【条件性风险】全屏游戏期间仍在做 Z 序/置顶操作，且**没有任何"游戏全屏就暂停"的闸门**

- **事实**：全项目 grep **不存在** fullscreen/游戏/D3D 判定 —— 程序永远不知道前台在跑全屏游戏。
- **位置与周期**：
  - `desktopmirrorwindow.cpp:200` `m_bottomTimer` **3000 ms** → `parkAllTargetsAtBottom()`（`:536`）
    → `SetWindowPos(s_dockHwnd, HWND_BOTTOM, ...)`，**无条件执行**（无 `s_desktopActive` 之外的任何豁免）。
    **Dock 是铺满整屏的窗口**。
  - `desktopmirrorwindow.cpp:718` `s_pollTimer` **150 ms** → `restoreAllTargets()`：每拍对每个受保护窗口做
    `IsIconic` + `IsWindowVisible` + `DwmGetWindowAttribute`（本机实测 ≈0 ms，故此项**降级为低风险**）。
  - `icongridwindow.cpp:2963` / `filesearchwidget.cpp:63` `m_layerKeeper` **1000 ms** → `ensureLayerAboveBandWindows()`
    （`:581`，遍历 Z 序链）→ 必要时 `raiseAboveBandWindows()` → `SetWindowPos`。
  - `desktopimmunityfilter.cpp:258-278` **300 ms** 节流复核：owner 变更时 `SetWindowPos(..., SWP_FRAMECHANGED)`。
  - `desktopmirrorwindow.cpp:3287` `WM_WINDOWPOSCHANGING` → `clampBandZOrder()` **改写每一次 Z 序变更**。
- **机理**：独占全屏（War3 是 DX8 老游戏）对 Z 序/窗口重排极其敏感，一次 Z 序操作可能触发显示模式切换
  ⇒ 1~3 秒黑屏 + 输入僵死。
- **诚实说明**：`DwmGetWindowAttribute` 本机实测 0 ms，**这条在当前桌面态下不构成负担**；
  它只在"游戏独占全屏"这一特定状态下才可能显形，**置信度低于 ②③**。

### ⑤ 【放大背景】360 系列 + 全机械硬盘在游戏期间的资源争抢

- **事实**：`ZhuDongFangYu.exe`（主动防御，会注入/扫描进程） + `360tray.exe` + `360DesktopService64.exe`
  + 十余个 `360se.exe`（单个 300~500 MB）同时在跑；游戏读盘期间三者抢同一批机械盘。
- **本机的 Shell 层真实水平**：`SHGetFileInfoW` 5~485 ms/项（正常机器通常 <1 ms）。
  其中 **485 ms 的那个项目正是 `360DesktopLite64.exe.lnk`** —— 360 自己的桌面组件让 Shell 查询变得极慢。
- **结论**：这条不产生卡顿，但**决定了长尾有多长**（决定了②③最终是 50 ms 还是 3 秒）。

### ⑥ 【固定尖峰】每 9 秒一次的回收站查询，永远在跑

- **位置**：`desktopmirrorwindow.cpp:210 m_recyclePollTimer->setInterval(9000)` → `pollRecycleBinState()`
  → `ShellOps::recycleBinIsEmpty()`（`shellops.cpp:140`）→ `SHQueryRecycleBinW(nullptr, &rb)`（**全盘**）
- **实测**：**48~61 ms/次**（C 盘 97 项 + F 盘 11 项），7×24 永不停。
- **判读**：不是 2~3 秒级，但**每 9 秒必然发生一次 50 ms 的 GUI 线程停顿** ⇒
  配合①的放大器，表现为"输入周期性发涩"。游戏读盘时会显著变长。

## 四、明确排除项（查过，不是它们）

| 候选 | 结论 |
|---|---|
| 鼠标低级钩子 `WH_MOUSE_LL` 每次移动同步往返 | **已根治** —— 鼠标已改 Raw Input（异步），正常路径不再有 `WH_MOUSE_LL` |
| 低级钩子数量叠加 | **不是问题** —— `dockiconbutton.cpp:152` / `desktopiconbutton.cpp:166` 那两套独立钩子**只在重命名编辑期间存在**（`installEditHooks`/`uninstallEditHooks` 成对），常态全进程只有 **1 个** `WH_KEYBOARD_LL` |
| 诊断日志落盘 | **已关闭** —— INI 无 `[Diagnostics]`、无 `DestopTools_trace.log`，`DiagTrace::enabled()` 为 false ⇒ 500 ms 落盘定时器根本不启动 |
| `CrashTrace::mark()` 同步写盘 | **不是** —— 实现只是 `strncpy_s` 内存拷贝（`crashtrace.cpp:162`），无文件 I/O |
| 剪贴板轮询 | **不是** —— `m_pasteWatcher`(120 ms) 只在粘贴流程内运行；`clipboardHasFileData()` 用 `IsClipboardFormatAvailable`，**不调用** `OpenClipboard`（不会因剪贴板被占用而阻塞） |
| 资源泄漏（GDI/句柄/内存） | **无** —— 实测 69 GDI / 581 句柄 / 0 缺页 |
| `GDI`/句柄耗尽 | **无** |
| `DwmGetWindowAttribute` 跨进程阻塞 | 本机实测 **≈0 ms**，桌面模式下无负担 |
| 跨进程 ListView 快照（`VirtualAllocEx`/`ReadProcessMemory`） | 本机实测 **0.02 ms/次**，不是瓶颈（代码注释的"数百毫秒"估计在本机偏悲观） |

## 五、可选的验证手段（都不需要改代码）

1. **二分法定位（最有效）**：用游戏全屏跑 20 分钟 → 关掉 `DestopTools.exe` 再跑 20 分钟。
   - 若关闭后完全不再卡 → 确认是本程序（①的放大器 + ②的扳机）。
   - 若仍卡 → 是 360 + 机械盘的独立问题。
2. **看是否"桌面有变化时才会卡"**：游戏期间不要新建/删除/下载任何文件到桌面根目录（`F:\Desktop`）。
   - 若"不碰桌面就不卡" → 锁定成因②（`SHChangeNotifyRegister` → `refresh()`）。
3. **打开诊断留痕**（现成开关，无需改代码）：
   设环境变量 `DESTOPTOOLS_DIAG=1` 再启动，会写 `release\DestopTools_trace.log`。
   卡顿发生时看该时刻的最后几行（`[restore]` / `[grid]`）即可判断卡在哪条路径上。
   ⚠️ 它会引入 500 ms 落盘定时器，**排查完请关掉**。
4. **抓现场（最硬的证据）**：卡顿发生时用 Process Explorer / `procexp` 看 `DestopTools.exe` 的
   哪个线程在等（栈里若出现 `SHGetFileInfo`/`SHParseDisplayName`/`IShellLink` 即命中成因②）。

## 七、一句话回答

**不是程序"坏了"，而是它把"系统级同步钩子（放大器）"和"GUI 线程上的整屏 Shell 查询（扳机）"
绑在了同一条线程上；平时只是偶尔发涩，一旦你玩游戏（机械盘被读满、360 同时在扫），
某一次 Shell 查询从 5 ms 涨到几百毫秒~几秒，钩子回调被拖住，全系统鼠标就跟着僵住 2~3 秒。**
